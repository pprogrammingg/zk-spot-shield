Merkle Inclusion

In Part 1 we chose option C: commit to one short fingerprint of the whole note set, then prove membership against that fingerprint. That technique is Merkle inclusion.

Why it fits: one registered root stands in for the whole tree; a spend only needs a short proof path, not the club list.

Roughly how: every note is a leaf hash. Pair leaves, hash each pair, keep going until one tip remains — the root. To spend, the guest recomputes your leaf, walks a short branch of sibling hashes, and checks the tip equals expected_root. Match → note is in the registered set. No match → fake or wrong tree; the proof fails closed.

Shared tree, next slot, and races

One more practical wrinkle: your private note (secret, balance) lives on the client. The membership tree is shared. User A’s deposits filled some leaf slots; user B’s filled others. When user C deposits, they need the next free slot — and when anyone spends, they need the current sibling path under a root the chain already approved. The client cannot invent that path from its own note alone.

So what is stored where? On Solana we keep the approved tip(s) as CleanFundsRoot accounts (and per-deposit leaf PDAs). The full append-order leaf list — the thing you rebuild the tree from — is not “the whole club roster dumped into one giant on-chain table.” In this demo the agent keeps that list locally. In a multi-user world you usually rebuild it from deposit history (on-chain leaf PDAs / txs, plus an optional append-only log).

What if B and C both fetch “next free slot = 5” and both try to write there? That collision is about the ordered tree index, not about overwriting each other’s on-chain leaf. Deposit leaf PDAs are keyed by the leaf hash itself (["deposit_leaf", leaf]), so two different notes do not fight for one PDA. But a Merkle tree needs one agreed append order: only one leaf can sit at index 5. If two writers race, you need a single sequencer for “next index” (one indexer / coordinator, or an on-chain counter that advances per deposit). The loser re-fetches and appends at the new tip; you never register a root built from two conflicting histories. This demo sidesteps the race with one local agent tree.

Seeing Merkle state without crawling everything

How do clients see the current Merkle state without crawling everything every time? Common patterns: (1) ask an indexer that watches deposits and answers “path for leaf i” / “next free index” quickly; (2) rebuild locally from the deposit log when you distrust the cache; (3) keep a short cache of path + registered root while proving. Indexers are convenience and speed — the guest still checks the path against the root, and settle still requires that root to be registered.
